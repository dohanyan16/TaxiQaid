## Mandatory session-transport decision

Supabase's [JWT claims reference](https://supabase.com/docs/guides/auth/jwt-fields) includes the account email, and the [custom-token-hook contract](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook) requires an email claim. Browser SDK `setSession` and subsequent user/refresh responses can expose the signed-in account's Auth email even if the broker omits email fields from JSON. Do not claim token redaction conceals it. This does not create a public username-to-email resolver, but it does not meet a literal requirement that **no internal email reaches the browser**.

The prepared SDK path stays disabled until this is resolved. If the owner requires strict internal-email secrecy, use a dedicated same-origin backend-for-frontend with opaque HttpOnly/Secure/SameSite session cookies and server-held Supabase tokens. That requires reviewed hosting and a replacement session bridge; static GitHub Pages cannot supply a same-origin server session layer. If the owner instead accepts standard own-session claims, that interpretation must be explicit before testing/activation. Do not strip a signed JWT, forge tokens or introduce magic-link/SMS/MFA steps to bypass the issue.

GitHub Pages may serve public static interface assets but does not protect operational records. Assess a dedicated authenticated origin/BFF, CSP and dependency integrity, cookie/CSRF controls where applicable, SDK token lifecycle, refresh/revocation and error/rate policies before employee deployment. A GitHub Pages origin may be shared across the owner's repository paths. Do not ship secrets, employee data or private documents in any static source/artifact. Staging memory sessions intentionally do not promise persistent login across reloads; production restoration must be tested with the approved session transport.

## Broker controls and configuration

The public endpoint accepts exactly `identifier` and `password` JSON, bounded to 4 KiB. Management usernames normalize to lowercase ASCII with no spaces/accents and remain stable after full-name changes. Approved unique suffixes belong to protected provisioning, not login. Driver identifiers are ten-digit Iqamas. Only Supabase Auth verifies passwords; none are stored in custom tables or Sheets. Unknown/incorrect/disabled/unlinked cases use generic errors. Failed created sessions are revoked. A minimum randomized response duration reduces obvious timing differences; it is not a replacement for abuse prevention.

CORS uses explicit origins, never a wildcard production allowlist. The counter transaction consumes HMAC-hashed client-IP, identifier and global buckets atomically before identity resolution/Auth. Proposed limits are 20/IP/minute, 10/identifier/15 minutes and 200/global/minute. They require owner/security review and concurrency testing. Counter failure denies login. A grant without a matching server-role RLS policy is insufficient; never disable RLS or grant browser roles to fix it. Retention cleanup and denial-of-service protections need deployment verification. Verify Supabase native Auth rate limits as well as broker limits; direct Auth password attempts must also be controlled. A platform/WAF must bound unauthenticated ingress and reject oversized/slow requests; CORS is not authentication or rate limiting.
