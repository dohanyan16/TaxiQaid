# User Management integration — disabled, not deployed

This branch implements the administrative persistence path. No hosted SQL, Auth account creation, Google connection, deployment, authentication activation or publication is authorized by this implementation. Dedicated frontend configuration remains `enabled:false`. Existing broker gates, Cloudflare, SQL rate limits, Cron, accounts and production `main` are unchanged. Earlier B2/B3 owner evidence is not repeated or extended to this service.

## Implemented boundary

`POST /functions/v1/manage-users` is a separate JWT-protected administrative function. The browser sends only its own SDK session JWT, public key, action and validated parameters. The function verifies that JWT online with official Supabase Auth, derives the actor UID from the verified response and rechecks current active account, enabled private mapping, active permission definitions, boolean overrides and dependencies in PostgreSQL on every call. Client role claims, metadata, submitted actor UID, API key alone and stale frontend permissions grant nothing. Driver identities are never provisioned.

All writes require the existing unique active Master (`super_admin`, visible label **Master**) and the corresponding capability. Master cannot be created, edited, disabled, reset or given overrides through this API. There is no role-name bypass around explicit Deny or dependencies. Authorized non-Master management users can read only with the relevant view capability; these readers see the administrative directory, so grant that capability deliberately. Manager and Supervisor start with no new defaults. New writes to existing role grants are not implemented.

| HTTP action | Required capability | Effect |
| --- | --- | --- |
| `list` | `user-management.view` | Management accounts, safe metadata, search and UUID pagination (maximum 100) |
| `create`, `recover-create` | `user-management.create-user` | Reserved, recoverable Auth/private provisioning; recovery uses existing operation UUID |
| `edit`, `reset-password`, `sync-auth`, `operations`, `sync-sheets` | `user-management.edit-user` | CAS edit/reset/status reconciliation; recovery receipts; separately gated mirror |
| status change within `edit` | also `user-management.change-status` | Private status and mapping suspension before Auth synchronization |
| `permissions` | `user-management.manage-permissions` | Validated boolean overrides by target UID, version and snapshot etag |
| `requests`, `request-enqueue` | `user-management.profile-requests.view` | Read queue; Master-only controlled intake with source explicitly unverified |
| `request-approve`, `request-reject` | `driver-profile.approve` / `driver-profile.reject` | Idempotent, versioned decision and history |

Internal `identity`, reservation, completion, recovery, synchronization and mirror lease operations are not accepted as HTTP actions. The SQL dispatcher alone is executable by the new runtime role. Its internal calls trust that restricted server connection, not browser roles. No general private SQL, arbitrary Auth user search or technical-email response is exposed to the browser.

Users shows UID, Username, Full Name, Contact Email, Role, Departments, Account Status, Updated At and Actions. Account Type/Status filters and Driver/Iqama creation controls are removed. Refresh performs an authenticated backend query; local search covers the loaded page and Refresh searches the server. The access selector uses these same records. Capability/User Permissions are the only matrix columns. Allowed/Denied reflect effective access; **unchanged selections produce no override**. Changing a selection produces a boolean override only for that key. An explicit Deny on a module suppresses dependent actions, without deleting their existing grants. Cancel reloads the selected snapshot. Inheritance cannot be explicitly restored with this two-state UI; a future independently reviewed action would be required to delete an override.

## Provisioning, failures and credentials

Creation uses a random operation UUID as the intended Auth UID, a private deterministic technical email, server-generated strong random password and protected **app_metadata** operation marker. SQL first reserves the unique normalized username/target with a two-minute lease. Official Auth Admin creates that identity initially banned; recovery may adopt only the exact UID/email/protected marker for the same reserved operation. Editable user_metadata is never authority. The handler validates the returned UID before completing the private account, private mapping and metadata/departments in one transaction. Native Auth is enabled only according to the intended active status; absent/incomplete private accounts never gain ERP access. No role grants are synthesized.

The Auth provider and PostgreSQL cannot share a transaction. Failure leaves an explicit recovery receipt and a quarantined/banned owned identity rather than silently deleting an uncertain identity. An ambiguous committed completion is confirmed from SQL and never re-created or given a second password. A recovery retains its lease while compensating, so another retry cannot race an old ban action; retry after expiry with the **same** operation. **Pending Provisioning** queries `operations` and offers a same-operation recovery button after the lease expires. **Retry Auth Sync** is available on accounts with a pending Auth synchronization. `operations` lists only the current Master's incomplete creation references/username/state; `recover-create` resumes the stored safe payload. The HTTP API does not expose private technical mappings. Unexpected provider UID/email/marker stops provisioning; leave the gate closed and reconcile through authorized Auth Dashboard inspection. Do not delete or recreate Master or an unrelated identity. Custom UID/marker behavior, eventual failures and orphan reconciliation remain live acceptance tests, not proven hosted by the mock provider.

Only a confirmed first creation/reset response can contain `temporaryPassword`, under no-store headers. SQL operation payloads, metadata, listings, audit and mirror never contain passwords or hashes. The UI masks this transient value, offers explicit Copy Once, clears it when closed or on session changes, and does not persist it. Deliver privately through an approved channel. Lost delivery requires a new authorized reset; replay cannot retrieve it. A reset operation is reserved before touching Auth; a failed/uncertain reset needs an explicit new operation after reconciliation. Passwords remain only in Auth. Mandatory first-login rotation is **not** claimed: arrange a protected official Auth password-change/recovery process before handing new accounts to users; it is not an email-login field or a Driver activation path.

Editing preserves UID and the private technical email; changing username changes the broker's existing exact username lookup. Private status/mapping changes commit first, invalidate mapping revision and block backend access immediately. Provider ban/unban failure is reported as `authSyncPending`; `sync-auth` uses a fresh current version/etag to reconcile. Replayed edits never reapply an obsolete Auth status. Every current protected administrative request rechecks live SQL authority. Existing frontend access leases still expire/revalidate using the established auth controller; already rendered UI is not authority and a cached JWT does not authorize a disabled account. The unchanged native Auth residual risk remains Option A; do not claim blanket native token revocation from a private-table update.

## Driver queue and Sheets

The queue and review history persist with UUID reference, Driver source reference, optional Iqama, name, field, old/proposed values, status/version, actor/time/note. `request-enqueue` is initially a controlled Master intake with **sourceVerified=false**. No Driver account, self-service write or authoritative source link is fabricated. Approval stores **approved_pending_application**, `applied=false`, and an explicit application blocker. There is no endpoint or SQL state that claims an authoritative Driver update. Rejection and retries retain history, CAS and idempotency. Actual Drivers-source application and portal submission remain blocked until a separately reviewed source/ownership integration.

The mirror is server-only and **disabled** until a separate Google authorization. `sync-sheets` returns DISABLED without any Google fetch or outbox claim when the flag is absent/false. Supabase is the authority; Sheets cannot write back permissions. Additional future secret names: `TAXIQAID_SHEETS_SYNC_ENABLED`, `TAXIQAID_GOOGLE_SPREADSHEET_ID`, `TAXIQAID_GOOGLE_ACCESS_TOKEN`, `TAXIQAID_GOOGLE_USERS_TAB`, `TAXIQAID_GOOGLE_REQUESTS_TAB`. No IDs, credentials or Google connection are configured by this branch. An expired OAuth access token leaves pending retries; secure token renewal/owner reauthorization and sheet sharing controls require a separate operational approval. No legacy Apps Script is used.

A coalescing outbox uses stable per-entity row numbers (start at 2), explicit RAW PUT ranges, versions, a two-minute global lease, maximum ten rows, bounded calls and exponential backoff. Retrying a lost response overwrites the same row instead of appending duplicates. Newer pending versions are not deleted by old acknowledgments. This is eventual mirroring, not cross-provider atomicity; after an ambiguous provider timeout, reconcile the latest Supabase version before treating a Sheet as current. Do not sort/move/delete the fixed machine-owned rows, reuse these dedicated tabs or grant them write-back authority. First-row headers and restricted sharing require owner preparation. Users mirrors only approved directory metadata; SQL removes contact values equal to known technical identity emails. Requests mirrors only reference/source reference, field, decision status/version/actor/time and minimized decision history, **not Iqama, names, old/proposed personal values or notes**. No actual authorized Driver changes exist to mirror yet. Payload allowlists fail closed; passwords, tokens and technical-email fields are never permitted.
