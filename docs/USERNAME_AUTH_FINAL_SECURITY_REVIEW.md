## Trusted client IP — activation blocker

Official Supabase sources consulted on the review date:

The documentation was retrieved from the official `supabase/supabase` repository; its observed master revision was [`afe5b4ed58586a43c7fd4cb05e49535b65629d66`](https://github.com/supabase/supabase/tree/afe5b4ed58586a43c7fd4cb05e49535b65629d66/apps/docs/content). Published documentation and the project's actual gateway behavior must both be considered.

- [Securing Edge Functions](https://supabase.com/docs/guides/functions/auth) and [authorization headers](https://supabase.com/docs/guides/functions/auth-headers): describe credential verification, not authenticated client-IP provenance.
- [Rate limiting example](https://supabase.com/docs/guides/functions/examples/rate-limiting): demonstrates atomic Redis limiting, not an ingress attestation contract.
- [Turnstile example](https://supabase.com/docs/guides/functions/examples/cloudflare-turnstile): reads the first `x-forwarded-for` value; this example is not proof that attackers cannot supply it. No Turnstile/challenge is proposed here.
- [Auth rate limits and IP forwarding](https://supabase.com/docs/guides/auth/rate-limits): a different Auth-server feature, requiring explicit enablement and a secret API key for `Sb-Forwarded-For`; publishable and legacy anon/service-role API keys are not supported for that forwarding feature.

The published material reviewed does **not establish a supported, non-spoofable end-user IP mechanism available to this hosted broker on every reachable ingress**. This is an evidence gap, not a claim that Supabase can never provide such a guarantee. `x-real-ip`, `cf-connecting-ip`, the first/last element of `x-forwarded-for`, `Forwarded`, caller-supplied headers and CORS are not independently authenticated IP sources. A socket address, if available, can identify a proxy rather than the browser. Correct IP syntax/canonicalization does not prove origin.

The current `trustedClientIp` parser rejects Forwarded/X-Forwarded-For, lists and malformed addresses and canonicalizes IPv6/mapped IPv4. It accepts a configured single-IP header **only after an external trust assertion**. `TAXIQAID_TRUSTED_IP_HEADER_VERIFIED=true` merely asserts that review happened; it cannot create the missing guarantee. Keep it false and login disabled. Do not select a plausible header, hardcode the owner's IP, trust a browser-supplied address, remove the IP bucket, substitute a shared IP bucket, or bypass the gate for a smoke test.

A practical installation-free next step is **Supabase Dashboard → Help/Support** (or the official support channel linked by the Dashboard). Ask for written confirmation of: (1) the supported authoritative address/header and exact single-value/list semantics, (2) strip/overwrite behavior for attacker-supplied copies and case/duplicate headers, (3) guarantees on the default project hostname, any custom hostname and alternate direct ingress, (4) whether peer metadata identifies the original client or only a proxy, and (5) ES256 gateway behavior for this project's deployment. Share only the project reference and sanitized questions, never secrets, tokens, IPs or private account data. Browser experiments alone cannot prove an ingress cannot be bypassed.

After a documented supported mechanism is identified, prepare a separately reviewed isolated spoofing/concurrency test and any minimal parser change. A trusted external gateway is only an architectural alternative if it authenticates its server-to-server assertions and **all direct broker bypasses are blocked**. Adding a custom domain/proxy alone does not do this. No gateway, new secret, browser challenge or deployment is introduced by this review. If Supabase cannot supply the guarantee under the current architecture, the first username test remains blocked pending an explicitly approved ingress redesign.

## Rate limiting findings

| Control | Reviewed behavior and limits |
| --- | --- |
| Atomic attempt consumption | `begin_login_attempt` calls the protected counter function before username/mapping lookup. Transactional UPSERT row locks serialize concurrent conflicts; no read-then-increment race. Denials commit earlier consumed buckets. Errors roll back and yield no identity/session. |
| Scope and values | HMAC-SHA256 domain-separated global, IP and normalized identifier buckets; fixed windows: global 200/60 seconds, IP 20/60 seconds, identifier 10/900 seconds. Same HMAC secret across instances is essential. Fixed-window boundaries permit bursts; these are not rolling-window limits. |
| Concurrency | Shared global-first lock order reduces deadlocks and caps accepted global attempts, but serializes traffic. The existing synthetic PostgreSQL harness checks 30 concurrent same-identifier requests allow at most 10; hosted capacity, pooler contention and independent-IP/global boundaries remain unverified. |
| Invalid/preflight traffic | Origin/readiness/input checks precede counters. Malformed requests and OPTIONS are not database-throttled. Global counters protect attempted identity resolution, not all edge invocations or infrastructure denial of service. CORS is not an authentication or non-browser abuse boundary. |
| Expiration/cleanup | Expired windows stop limiting new windows; rows do not disappear automatically. `prune_login_counters` removes at most 1,000 rows per call, only expired more than five minutes, with SKIP LOCKED. Runtime cannot invoke it. No verified recurring cleanup/monitoring schedule is established. Retention, cadence, bounded repeat batches and alerting require owner review; never delete live buckets or recreate the table. |
| Outages | Untrusted/missing IP, connection/TLS/SQL failures and malformed mapping/access replies fail closed; no in-memory limiter fallback. A counter transaction that fails can roll back consumption, but must not release an identity. Cleanup failure must alert without opening login. |
| Enumeration | Unknown/disabled identifiers receive no mapping, use a reserved invalid dummy Auth target and generic errors. Wrong credentials use the same public message. HMAC buckets hide raw identifiers/IPs in counters. HTTP status and timing can still differ on dependency/rate failures; jitter is padding, not a constant-time guarantee. Privately test known-wrong/unknown behavior and avoid repeated Master lockout tests. |
| Native Auth bypass | `/auth/v1/token?grant_type=password` remains directly reachable with the public project key. Broker counters do not protect this route, recover/signup/refresh routes or an attacker who knows an email. The accepted own-session email claim means technical emails cannot be treated as permanent secrets. Native Auth abuse controls remain necessary. |

Official Auth limits use token buckets and HTTP 429. The current [official limits table](https://github.com/supabase/supabase/blob/master/apps/docs/content/_partials/auth_rate_limits.mdx) includes password, refresh, ID-token and PKCE grants under `/auth/v1/token`; do not infer password limits from the email/SMS limits or assume a fixed quota from memory. Inspect actual project settings under **Authentication → Rate Limits**. Broker-to-Auth requests use the publishable key: native Auth may observe shared Edge egress, so aggregate throttling and availability require capacity testing. Do not add a broad secret key or pretend an untrusted forwarded header fixes this. Native quotas, direct-endpoint coverage and retained request-log privacy are unresolved live configuration checks; no CAPTCHA or MFA is introduced.

5. The permission model preserves 107 definitions, 101 Master grants, explicit Deny before Allow/inheritance, module dependencies and management/Driver audience separation. Inactive definitions/departments are filtered in the backend proposal. Boolean overrides convert true→allow, false→deny, no row→inherit. Existing live response compatibility must still be confirmed; counts alone do not prove every permission is correct.
6. Dedicated frontend state is disabled and staging sessions are memory-only. Logout clears access; expiry/identity changes fail closed; stale responses cannot restore authority. Thirty-second refresh/short leases bound stale app authorization rather than instantly revoking every JWT. Direct Auth may still issue a session for an app-disabled account: authorization must continue to deny private/business access. Logout revokes the local refresh session; already issued access JWTs can survive until expiry. No mandatory MFA is added; AAL1 password-only operation is required.
7. The isolated browser helper clears the password, blocks browser persistence and prints only whitelisted statuses/counts/presence/HTTP codes. Standard own-session email claims are owner-approved; arbitrary mappings/raw account responses are forbidden. Review platform logging, third-party scripts/dependency integrity and failed cleanup before employee activation. Mocked privacy checks do not audit provider retention.
