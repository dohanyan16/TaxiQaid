## Recommendation

| Scope | Earlier proposal | Recommended controlled pilot | Future production |
| --- | --- | --- | --- |
| Global | 20 attempts/60 seconds | **20 attempts/60 seconds** | Size from forecast burst and measured downstream capacity; no approved higher value yet |
| Verified source IP | 2 attempts/60 seconds | **10 attempts/60 seconds** | Size for the largest legitimate shared NAT burst; do not assume one IP means one person |
| Normalized identifier | 10 attempts/900 seconds | **10 attempts/900 seconds** | Retain 10/900 initially; change only after separate abuse/usability review |

These are fixed windows anchored to database epoch time. They count **attempts, including successful authentication**, not unique people or only wrong passwords. The identifier budget does not multiply with source addresses. Ten successful re-logins can also exhaust that account's window; preserve normal sessions rather than repeatedly testing passwords. Driver login remains disabled; this pilot is for provisioned management accounts only. Driver shift demand must be included in future planning before driver provisioning/activation is approved.

Two attempts/IP/minute is suitable for a narrow owner diagnostic, not an employee rollout. Ten improves shared-network usability without increasing the global downstream allowance. It also permits five times as many admitted guesses across identifiers from one address as the earlier IP cap; this is a conscious pilot tradeoff, not a security-neutral increase. A hypothetical office burst of five people making two attempts each uses ten IP attempts; two such offices use the twenty global attempts. This is an illustration of the policy, not observed traffic or a promise that twenty sessions can be created in a minute. A sixth person behind that office NAT may be denied. Twenty-one distinct first-attempt logins can hit the global cap; no finite IP threshold can reliably distinguish people sharing a carrier address.

Approve only a small, scheduled, supervised pilot whose expected attempts fit both budgets, with no automatic retries and an operator able to close the window. Enrolment size is not a rate estimate: agree the maximum simultaneous login/retry pattern first. Do not roll out this pilot setting to the whole future workforce.

## Shared NAT, shift changes and availability attacks

Office Wi-Fi, VPNs and carrier NAT share an IP allowance. IPv6 privacy addresses, proxies and distributed clients can spread guessing across many IP allowances. The stable identifier bucket remains important. Clock-boundary bursts can admit up to twice a fixed-window threshold in a very short interval, including twenty guesses near an identifier-window boundary. This is not a sliding fifteen-minute lockout. A queue, retry or browser delay does not increase backend capacity; clients should stop on 429, wait until the window can recover, and avoid synchronized repeated retries. Current generic 429 responses do not promise an exact reset time.

The SQL consumes **global, then IP, then identifier** in a common lock order. Earlier buckets remain consumed on denial. In particular, requests already blocked by their IP still spend global allowance. One source can exhaust the twenty global attempts; a distributed attack is not necessary. Identifier-targeted requests can also deny the real user's ten-attempt allowance for up to the remainder of fifteen minutes. Increasing thresholds trades usability against guessing and downstream load; it does not fix this denial-of-service property.

The global bucket is a resource circuit breaker, not a fairness guarantee. It bounds attempts reaching password verification but does not bound inbound HTTP requests, denied counter updates, connection attempts, lock contention, Edge invocations or Worker billing/quota use. Requests denied at global still perform a database update. Saturating counter values indicate budget exhaustion; they are not exact request-volume or unique-user measurements. The global counter row is a contention point; short lock/statement timeouts fail closed and may reject legitimate traffic during a burst. The existing restricted connection limit must remain intact. No universal availability guarantee is possible against deliberate saturation on these Free services.

An optional future Cloudflare edge limiter/challenge could reject more abuse before it reaches SQL. Its design, accessibility impact, cost and gateway bypass closure need separate review. Cloudflare's [rate-limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) is approximate and local to a Cloudflare location; it cannot replace the exact shared database limits. No binding, challenge or alternate route is added by this review. Production rollout remains blocked until the owner explicitly accepts this pilot availability risk and later validates adequate ingress protection and capacity for broad use.

## Success, failure and enumeration

Every well-formed, authorized gateway request that reaches the atomic counter function spends attempts before private username/mapping lookup and official password verification. Known/unknown usernames, disabled accounts, wrong passwords, successful passwords, native Auth errors and subsequent access/mapping failures use the same admission stage. Replays consume limits but cannot release a second usable attempt. No successful-login reset, refund or outcome-specific public counter is introduced. Malformed requests, invalid gateway proofs, disabled configuration and stale cleanup health fail before that stage. Transaction failure can roll back its counter changes; it must return failure without continuing to Auth.

Charging all admitted attempts keeps one consistent prelookup security boundary. A successful-password refund could be abused with a known credential, races with concurrent attempts, and would need a separately reviewed reservation/finalization protocol. Failed-only counters would still need a gross-attempt circuit breaker. Native Auth refreshes bypass this broker counter stage and have their own quota.

Unknown and disabled identifiers retain the dummy Auth check and the same generic response as bad credentials. 429 does not disclose the exhausted scope or account existence. Normalization and HMAC bucket domains remain unchanged; no raw identifiers or IPs are stored in counters or reported by test helpers. Generic errors and jitter reduce enumeration signals; they do not prove constant-time behavior. Keep password-strength/provisioning policy, native protections and telemetry review; ten attempts per identifier is only one guessing control. A malicious caller can target a known username or many usernames regardless of CORS.

The gateway seals access to **the custom broker**, not to all of Supabase Auth. Direct native password/refresh endpoints still exist and rely on native abuse controls; technical emails in the user's own genuine session claims are acceptable and must not be treated as a secret security boundary. No public username/email lookup or broker fallback is allowed. Existing UID, active status, mapping-revision and 101/six access checks remain mandatory after password verification.

## Supabase Free and native Auth constraints

Keep the owner's verified native settings unchanged: sign-up/sign-in operations 30/5 minutes/IP; token grants, including password and refresh, 150/5 minutes/IP; OTP verification 30/5 minutes/IP; anonymous sign-in 30/hour/IP; IP forwarding disabled. These are **different endpoint buckets**, not cumulative allowances that can be added or a blanket thirty-password-login quota. The [official rate-limit documentation](https://supabase.com/docs/guides/auth/rate-limits) describes IP token buckets with burst behavior. Read actual endpoint errors and Dashboard settings during approved tests; do not infer an effective Edge-egress distribution from frontend IPs.

For conservative planning, assume broker password calls can share one native-Auth egress-IP budget. Do not multiply the native quota by the number of end users or invent an egress-IP count. Six fixed minute buckets can overlap a five-minute interval: 20 × 6 = 120 broker admissions is an arithmetic upper bound before other constraints, not guaranteed native capacity. The nominal difference from 150 is not reserved headroom. Native burst capacity, bucket refill timing, other server traffic, direct password grants and refresh requests can still cause 429. The documented token-endpoint burst capacity is thirty: two adjacent global windows can release forty admissions faster than that bucket refills, so even an otherwise idle deployment can receive native 429 at a boundary. Increasing the pilot IP budget does not increase this global bound.

The frontend's thirty-second access revalidation, SDK session establishment, online user verification, `get-my-access`, sign-out and future refreshes add load beyond one password POST. The current official [Auth router source](https://github.com/supabase/auth/blob/master/internal/api/api.go) places the User limiter on PUT `/user`, rather than GET `/user`. This source review is not verification of the project's deployed version or every platform control: do **not** claim each SDK `getUser()` spends the 30/5-minute sign-up bucket merely because the docs list `/user`. Verify the real request mix and response statuses. A concurrent-session refresh storm can consume native token allowance even if no new broker attempts are admitted.

The [Free compute documentation](https://supabase.com/docs/guides/platform/compute-and-disk) describes shared Nano resources and separate database/pooler connection ceilings. Account/MAU, storage, function-invocation and connection quotas are not guaranteed password-check throughput. Free database pause behavior, Cron execution, pool occupancy, hot-row locks, statement timeouts, Auth latency and Worker/Edge quotas must be checked. This review contains **no hosted load measurements**, provider throughput guarantee or promised employee capacity. Local PostgreSQL tests below validate correctness, not Supabase performance.

## Configurable policy and production sizing

`supabase/review/public-login/rate-limit-policy.json` is the single reviewed **build-time** input. The generator emits literal arrays into standalone `00_conservative_limits.sql`; the owner can still use only GitHub and Dashboard. No JSON fetch, policy table, new database privilege, session GUC, environment override, client parameter or runtime fallback is introduced. All broker instances share the atomic database policy after a separately approved complete SQL transaction. Generating or committing a file does not apply it.

The validator permits integer pilot values only: global 2–20, IP 1–19 and strictly below global, identifier 1–10; windows stay 60/60/900 seconds. The IP/global separation lets the isolated live IP probe reach IP denial before global denial. The recommended profile is 20/10/10. Changing these ceilings, windows or the profile to production requires explicit code/security review, not silently increasing a JSON value. Lower thresholds also require review and regression testing. Do not rotate the rate HMAC secret, vary the global key or clear counters to evade an existing denial.

For future production, collect the busiest minute's forecast login attempts **including retries**, the largest per-NAT attempt burst, and the five-minute password/refresh mix for each actual native egress/client-IP grouping. Use the full burst if users all arrive together; dividing a shift's headcount by its nominal login window can conceal a first-minute surge. Choose global and IP thresholds at least large enough for the agreed legitimate peak plus an explicitly approved retry margin, while remaining inside tested downstream sustained and burst capacity. Keep the identifier limit initially ten per fifteen minutes. Evaluate adjacent-minute boundary bursts and concurrent refresh demand, not just average requests/minute.

For example, a *hypothetical* 60 distinct first-attempt logins in one minute needs at least global 60; if 30 share a NAT it needs at least IP 30 before any retry margin. Those numbers are **demand arithmetic, not recommended or approved settings**. At global 60, six minute buckets allow up to 360 admissions overlapping five minutes, already exceeding the owner's 150 native sustained setting under a shared-egress assumption. Raising SQL limits alone cannot qualify that rollout. Stage logins, reduce validated avoidable load, or separately review suitable provider capacity/architecture; no settings change or privileged key is authorized here. Production numeric limits remain unapproved until forecasts, abuse controls and genuine tests support them.
